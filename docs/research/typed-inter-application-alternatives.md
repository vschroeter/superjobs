# Typed communication between independently deployed applications

As of 2026-10-05. Assessment of SuperJobs' scope against established alternatives.

## Evidence and limits

**Documented** means an official documentation claim; **Code** means a public source signature; **Assessment** means a conclusion drawn from those capabilities. No alternative was installed, executed, benchmarked, or checked with a static checker during this investigation. Mutable documentation and default-branch sources are point-in-time evidence, not a tested feature matrix. Local domain language: [GLOSSARY.md](../../GLOSSARY.md), [API](../api.md), and [the earlier job queue comparison](job-queue-api-comparison.md).

## Decision boundaries

**Assessment:** Independently deployed virtual environments and containers do not by themselves justify a new communication library. The important distinction is the operation: publishing data, calling an available service, submitting a durable job, or coordinating a durable workflow. All can involve typed payloads, but their lifetime and failure semantics differ.

| Need | Existing option and documented evidence | Assessment for SuperJobs |
| --- | --- | --- |
| Python applications publish telemetry, manifests, or domain events through NATS | **Documented:** FastStream consumes messages using annotated function parameters and Pydantic validation; JSON is the default format with customizable decoders. It supports NATS and JetStream, standalone publishing, request/reply, and AsyncAPI export. [Validation](https://faststream.ag2.ai/latest/getting-started/subscription/), [serialization](https://faststream.ag2.ai/latest/getting-started/serialization/), [NATS](https://faststream.ag2.ai/latest/nats/), [publishing](https://faststream.ag2.ai/latest/nats/publishing/), [RPC](https://faststream.ag2.ai/latest/nats/rpc/), [AsyncAPI](https://faststream.ag2.ai/latest/getting-started/asyncapi/export/). | FastStream is the first comparison to run for this broad requirement. A shared payload package can supply application contracts. Its documented RPC example returns a `NatsMessage`; it does not establish the same generic request/result/event Job-handle contract as SuperJobs. That observation does not rule out wrappers or extensions. |
| Typed service calls across programming languages | **Documented:** gRPC defines service methods and their input/output messages in Protobuf and generates clients and servers; clients and servers can run in different environments and languages. Unary and streaming calls are supported. [Introduction](https://grpc.io/docs/what-is-grpc/introduction/), [core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/). | A strong default for direct service APIs and future non-Python consumers. A durable execution handle with retained results after callers disconnect requires an application protocol beyond the basic RPC lifecycle. |

## The defensible SuperJobs niche

**Assessment:** SuperJobs has a plausible niche as a Python-first Job contract and execution-observation layer over an existing NATS deployment: one worker-free package defines the request, result, and intermediate-event types; producers submit work through that contract and can reconstruct a typed handle later. The combined developer experience can be useful even though none of “NATS,” “typing,” “separate programs,” or “containers” is unique. The rationale is strongest when work must survive caller disconnection, has a retained final result, and needs typed progress/events and cooperative cancellation.

The local domain model describes one load-balanced pool per Job, with intermediate events permitted to be lost on worker failure. **Assessment:** This is a job abstraction, not the natural default for distributing each telemetry occurrence to multiple independent subscribers. Schema compatibility between deployed contract versions also remains a separate concern: a shared Python package helps coordinate definitions but is not sufficient to prove compatible rolling upgrades. Protobuf explicitly distinguishes safe, unsafe, and conditionally safe wire changes. [Local domain language](../../GLOSSARY.md), [Protobuf schema evolution](https://protobuf.dev/programming-guides/proto3/#updating).

**Recommendation, not a new implementation decision:** Validate the niche with one real application slice against FastStream for simple data exchange and Taskiq plus a small contract wrapper for durable jobs. Require separate producer/worker environments, wrong-payload rejection, consumer typing, reconnectable observation, and failure recovery. Continue SuperJobs if its API materially reduces application glue while its reliability semantics remain testable. Avoid expanding into general messaging or workflow orchestration merely to justify maintaining a new library.
