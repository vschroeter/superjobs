# Job queue APIs for separate programs

> **Historical status (2026-10-03):** Comparative research for issue [#2](https://github.com/vschroeter/superjobs/issues/2)
> (2026-09-28). Informed shared-contract and handle design; not a live API comparison
> matrix. Current behavior: [api.md](../api.md), [ADR 0001](../adr/0001-shared-contract-packages.md).

As of 2026-09-28. Investigation for [Research: compare job queue interfaces for separate programs](https://github.com/vschroeter/superjobs/issues/2), part of the [Wayfinder map](https://github.com/vschroeter/superjobs/issues/1).

SuperJobs can distinguish itself through an explicit, worker-free contract for request, result, and intermediate events. Named dispatch and Python typing alone are not unique selling points: Taskiq and current Dramatiq already offer both. The product decision is to expand a shared Python contract package and the typing/test foundation first.

## Evidence and limits

**Doc** denotes a documented commitment; **Code** a read signature/implementation; **Derivation** our design assessment. Only official documentation and project sources were used. Reference snapshots: Celery docs 5.6.3, Dramatiq docs/tag 2.2.0, arq docs 0.28.0; Taskiq docs and linked `master` sources are mutable point-in-time snapshots. No comparison library was executed or statically checked here; signatures are evidence of existing mechanisms, not proof of flawless inference in every consumer.

Local starting point: [GLOSSARY.md](../../GLOSSARY.md) separates Job, Job execution, Attempt, and Job handle. [Job](../../src/superjobs/jobs/job.py), [JobClient](../../src/superjobs/jobs/job_client.py), and [JobHandle](../../src/superjobs/jobs/job_handle.py) already carry request/result/event type parameters. `py.typed` is present. At the start of the investigation [pyproject.toml](../../pyproject.toml) contained no static checker; the lead agent reported as measured baseline 140 tests without NATS and six NATS tests, the latter within one process. This research did not repeat that measurement.

## Dispatch, contracts, and types

| Library | Producer without handler import | Types and bounds of named invocation |
| --- | --- | --- |
| Taskiq | **Code:** `AsyncKicker(task_name, broker, labels, return_type=...)` sends by name. A local handler definition is not required for that. | **Code:** `AsyncKicker[P, R]` and `AsyncTaskiqDecoratedTask[P, R]` take `ParamSpec` and result type; `kiq` yields `AsyncTaskiqTask[R]`. **Derivation:** From the string name alone no argument signature arises; a worker-free producer must declare its types explicitly or use a shared typed wrapper. [Kicker](https://github.com/taskiq-python/taskiq/blob/master/taskiq/kicker.py), [Decorator](https://github.com/taskiq-python/taskiq/blob/master/taskiq/decor.py). |
| Celery | **Doc:** `send_task(name, args, kwargs, ...)` is explicitly intended for tasks not registered in the local process. | **Code/Doc:** Named dispatch offers no request/result generics derived from the name. `pydantic=True` validates/converts in the worker and serializes its result; the producer still serializes arguments itself. This runtime validation does not replace a shared static producer contract. [Calling API](https://docs.celeryq.dev/en/stable/userguide/calling.html), [send_task](https://docs.celeryq.dev/en/stable/reference/celery.html#celery.Celery.send_task), [Pydantic](https://docs.celeryq.dev/en/stable/userguide/tasks.html#argument-validation-with-pydantic), [Result code](https://docs.celeryq.dev/en/stable/_modules/celery/result.html). |
| Dramatiq | **Doc:** The published message format allows dispatch by `actor_name`, even from other languages. **Code:** Python can construct such `Message` objects as well. | **Code:** In 2.2.0, `Actor[P, R].send(...) -> Message[R]`, and `Message[R].get_result() -> R`. When constructing directly, however, `args`/`kwargs` remain `Any`; a result annotation does not automatically tie the string name to worker types. [Message format](https://dramatiq.io/advanced.html#enqueueing-messages-from-other-languages), [Actor 2.2.0](https://github.com/Bogdanp/dramatiq/blob/v2.2.0/dramatiq/actor.py), [Message 2.2.0](https://github.com/Bogdanp/dramatiq/blob/v2.2.0/dramatiq/message.py). |
| arq | **Doc:** `enqueue_job('function_name', ...)` was deliberately chosen to separate frontend and worker code. | **Code/Doc:** `enqueue_job(function: str, *args: Any, **kwargs: Any) -> Job | None`; `Job.result() -> Any`. **Derivation:** The separation is pleasant, but static request/result linking requires an additional contract/wrapper. [Design and Job API](https://arq-docs.helpmanual.io/), [enqueue_job code](https://arq-docs.helpmanual.io/_modules/arq/connections.html). |

**Events:** Taskiq has progress queries; the handle considered returns `TaskProgress[Any] | None`. Celery documents `update_state(..., meta={...})` and `on_message`. In the considered public submit/handle APIs of Dramatiq and arq, no shared generic request/result/event contract is exposed. That is a limited API observation, not a statement about every extension. **Derivation:** SuperJobs should model progress, intermediate events, and final result separately and preserve their types through to the consumer. [Taskiq handle](https://github.com/taskiq-python/taskiq/blob/master/taskiq/task.py), [Celery Progress](https://docs.celeryq.dev/en/stable/userguide/calling.html#on-message), [Dramatiq Message](https://github.com/Bogdanp/dramatiq/blob/v2.2.0/dramatiq/message.py), [arq Job](https://arq-docs.helpmanual.io/#arq.jobs.Job).

## Handles, retry, cancel, and lifecycle

- **Taskiq – Code/Doc:** `AsyncTaskiqTask(task_id, result_backend, return_type)` can be reconstructed; `get_result`/`wait_result` yield a result container. `SimpleRetryMiddleware` and `SmartRetryMiddleware` offer configurable retries; the considered simple-retry code reuses the same task ID. `with_task_id` is therefore not a documented idempotency guarantee. The considered core handle has no cancel method. Client/worker startup and shutdown have separate events; clients start and close the broker explicitly. [Handle](https://github.com/taskiq-python/taskiq/blob/master/taskiq/task.py), [Retry docs](https://taskiq-python.github.io/available-components/middlewares.html), [Retry code](https://github.com/taskiq-python/taskiq/blob/master/taskiq/middlewares/simple_retry_middleware.py), [Kicker](https://github.com/taskiq-python/taskiq/blob/master/taskiq/kicker.py), [Lifecycle](https://taskiq-python.github.io/guide/state-and-deps.html).
- **Celery – Doc:** `AsyncResult(id)` can be restored; result availability depends on the backend. Retry keeps the task ID and can use backoff/jitter. `revoke()` usually prevents start but does not stop an already running task; `terminate=True` terminates the worker process and is documented as an administrative emergency measure. Worker/process lifecycle has signals; shutdown hooks are not guaranteed on process loss. By default acknowledgment happens before execution; `acks_late` and `task_reject_on_worker_lost` change different parts of redelivery behavior. [Results](https://docs.celeryq.dev/en/stable/reference/celery.result.html), [Retry and acks](https://docs.celeryq.dev/en/stable/userguide/tasks.html), [Revoke](https://docs.celeryq.dev/en/stable/userguide/workers.html#revoke-revoking-tasks), [Signals](https://docs.celeryq.dev/en/stable/userguide/signals.html).
- **Dramatiq – Code/Doc:** The immutable `Message[R]` is a result reference; reconstruction needs message metadata and backend, not only a universal ID handle. Results require optionally enabled results middleware. Failures are retried with backoff; actor idempotency is assumed. Graceful shutdown requeues open messages; process loss can trigger redelivery. Lifecycle is extended via middleware hooks. The official cancel recipe points to `dramatiq-abort`; that is an extension, not a core commitment verified here. [Message](https://github.com/Bogdanp/dramatiq/blob/v2.2.0/dramatiq/message.py), [Results and shutdown](https://dramatiq.io/advanced.html), [Retries](https://dramatiq.io/guide.html#message-retries), [Middleware](https://dramatiq.io/reference.html#middleware), [Cancel recipe](https://dramatiq.io/cookbook.html#aborting-messages).
- **arq – Code/Doc:** `Job(job_id, redis, ...)` is reconstructible. `_job_id` prevents re-enqueueing while job or stored result exists; duplicates return `None`. The code checks the ID, not a payload fingerprint. `Retry(defer=...)`, `max_tries`, worker startup/shutdown, and job hooks exist. `Job.abort()` requires `allow_abort_jobs=True`; worker shutdown can abort running work and run it again later. **Derivation:** ID uniqueness and idempotent side effects are different commitments. [Job/shutdown](https://arq-docs.helpmanual.io/), [ID check](https://arq-docs.helpmanual.io/_modules/arq/connections.html), [Worker](https://arq-docs.helpmanual.io/_modules/arq/worker.html).

## NATS limits for the SuperJobs contract

**Doc:** Core NATS delivers at most once; for durable jobs SuperJobs needs JetStream. A `PubAck` confirms storage, not worker execution; a publish timeout can occur even after successful storage. `Nats-Msg-Id` deduplicates only within the configured stream time window. [Core NATS](https://docs.nats.io/learn/core-nats/), [JetStream Publishing](https://docs.nats.io/learn/jetstream/publishing).

**Doc:** Without ack, redelivery happens after `AckWait`. `in-progress` extends that window; too short `AckWait` can cause parallel processing of the same request. Double ack (`ack_sync` in the Python client) waits for server-side acknowledgment of the ack. `MaxDeliver` limits deliveries but does not create a SuperJobs error or an automatic dead-letter queue; the message remains in the stream and an advisory must be handled separately. [Acks](https://docs.nats.io/learn/jetstream/delivery-and-acknowledgment), [Redelivery](https://docs.nats.io/learn/jetstream/acknowledgment).

**Derivation:** A crash between external side effect and completion record/ack remains possible. Publish deduplication plus double ack does not yield general exactly-once execution. SuperJobs needs a durable completion record for redelivery reconciliation and clearly declared at-least-once semantics; handlers need their own idempotency for external effects. Result retention and deduplication windows belong in the API commitment, not merely in transport configuration. This follows from the separate storage/ack steps and the redelivery evidence above; it is not an already measured SuperJobs proof.

## Four focused recommendations

1. **Make the shared job contract the stable entry point.** Request, result, and event types plus name/version live in the contract package; workers register implementations separately. An example with a producer without an installed worker package must prove that decoupling. Taskiq/Dramatiq show that good generics are possible; arq shows the benefit of import separation. The ergonomic win must combine both.
2. **Prove typing as a consumer property.** A fixed static checker exercises public imports from the built/installed distribution. Positive examples prove submit, reconstructed handle, `result`, `outcome`, and event iterator; negative examples must actually reject wrong requests, handler results, and events. `None` contracts and accidental `Any` need cases too. These criteria are a proposal, not an outcome of this research.
3. **Make handle and lifetime explicit.** Submission, observation, and waiting should be usable independently; another client reconstructs the same typed handle. Wait timeout, attempt timeout, execution deadline, cancellation request, and terminal outcome get distinguishable semantics. A short lifecycle with clear resource responsibility is preferable; the final runtime/client form remains a design decision.
4. **Prove reliability in three layers.** Deterministic in-memory cases check state transitions; real JetStream tests check publish/ack/redelivery/retention; separately started producer/worker processes check import separation and recovery. Crash cases must hit the gap between handler, completion record, and ack. An explicitly required NATS test run must fail when the environment is broken. Measure latency/throughput targets afterward; this research does not justify a performance ranking.

## Open design decisions

These questions remain separate decisions on the Wayfinder map and are not decided by this report:

- What concrete handler and runtime registration form offers the most pleasant API without binding the contract package to worker lifecycle or broker instances?
- For handle reconstruction, is the combination of job contract and execution ID enough, or should a serializable reference also carry name/version/backend address?
- How does version/schema incompatibility behave between installed contract packages, and what validation strictness applies when decoding? A shared package reduces drift but does not prevent different installed versions.
- What idempotency, completion-record, and result-retention limits are committed; how are conflicting payloads under the same idempotency key handled?
- Which cancel races and observation loss belong to the public commitment? The domain language names cooperative cancellation and non-crash-safe intermediate events; the exact API and test cases must make that concrete.
